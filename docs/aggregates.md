## Aggregate Basics

An aggregate is the fundamental building block of event sourcing and Domain-Driven Design. It represents a cluster of domain objects that can be treated as a single unit for data changes.

### Key Principles

1. **Consistency boundary**: Aggregates enforce invariants
2. **Transactional boundary**: Changes to an aggregate are atomic
3. **Event-sourced**: State is derived from events
4. **Identified**: Each aggregate has a unique `EntityId`
5. **Versioned**: Optimistic concurrency control

## Defining Aggregates

### The Aggregate Pattern (Recommended)

The **recommended approach** is to use `#[aggregate(...)]` which generates both `Entity` and `Aggregate` trait implementations:

```rust
use event_sauce_core::EntityId;
use event_sauce_macros::AggregateError;
use thiserror::Error;

// Define aggregate error (auto-implements AggregateError)
#[derive(AggregateError, Debug, Error)]
enum AccountError {
    #[error("Insufficient funds")]
    InsufficientFunds,
}

// Define the aggregate - contains the ID field and all business data
#[aggregate(event = "AccountEvent", error = "AccountError")]
#[derive(Default)]
struct BankAccount {
    #[id]
    id: EntityId,
    owner: String,
    balance: i64,
    status: AccountStatus,
}
```

All entities use `EntityId` (a UUID-backed concrete newtype) as their identifier. No custom ID types are needed.

**Important**: The `EventApplicator` trait impl is auto-generated by the `#[event(aggregate = "BankAccount")]` attribute on your Event enum. You implement `ApplyEvent` trait for each event struct, and the macro generates the dispatching logic automatically via `EventApplicator`.

### What Gets Generated?

The `#[aggregate(...)]` macro generates `Entity` and `Aggregate` trait implementations:

```rust
// GENERATED CODE (you don't write this!)

// Entity trait implementation
impl Entity for BankAccount {
    fn new(id: EntityId) -> Self {
        Self {
            id,
            owner: Default::default(),
            balance: Default::default(),
            status: Default::default(),
        }
    }

    fn entity_id(&self) -> EntityId {
        self.id
    }
}

// Aggregate trait implementation
impl Aggregate for BankAccount {
    type Event = AccountEvent;
    type Error = AccountError;
}
```

Infrastructure concerns (version tracking, pending events, event application) are handled by `AggregateRoot<BankAccount>`:

```rust
// AggregateRoot wraps your entity with infrastructure
let mut account = AggregateRoot::<BankAccount>::new(EntityId::new());

// Read-only access to entity fields via Deref
println!("Balance: {}", account.balance);

// Infrastructure methods on AggregateRoot
println!("Version: {}", account.version());
println!("Pending events: {}", account.pending_events().len());

// State changes must go through apply()
account.apply(some_event)?;
```

### Benefits of the Entity/AggregateRoot Pattern

1. **Clear separation**: Entity contains only business state, `AggregateRoot` handles infrastructure
2. **Read-only Deref**: `AggregateRoot<A>` implements `Deref<Target = A>` but not `DerefMut` -- all mutations go through `apply()`
3. **Less boilerplate**: The `#[aggregate]` macro generates both `Entity` and `Aggregate` impls
4. **Universal ID**: All entities use `EntityId`, no custom ID types needed
5. **Type safety**: Events are the only path to state mutation

### Aggregate Attributes

- **`event`**: The event type for this aggregate (required)
- **`error`**: The error type for this aggregate (optional, defaults to `()`)
- **`#[id]`**: Field attribute marking the `EntityId` field (or name it `id`)

### Key Features

- **`#[id]` field attribute**: Marks which field is the entity ID (must be `EntityId` type)
- **`EntityId` for all entities**: Concrete UUID-backed newtype, no custom ID types
- **`AggregateRoot<A>` wrapper**: Handles version, pending events, and event application
- **Read-only Deref**: Access entity fields directly through `AggregateRoot`

## Aggregate Errors

Aggregate-specific errors provide rich, domain-specific error handling.

### Defining Aggregate Errors

Use `thiserror` for clean error definitions with `#[derive(AggregateError)]`:

```rust
use thiserror::Error;
use event_sauce_macros::AggregateError;

#[derive(AggregateError, Debug, Error)]
enum BankAccountError {
    #[error("Insufficient funds: balance={balance}, requested={requested}")]
    InsufficientFunds {
        balance: i64,
        requested: i64,
    },

    #[error("Invalid amount: {0} (must be positive)")]
    InvalidAmount(i64),

    #[error("Account is {0:?}")]
    AccountNotActive(AccountStatus),

    #[error("Withdrawal limit exceeded: limit={limit}, requested={requested}")]
    WithdrawalLimitExceeded {
        limit: i64,
        requested: i64,
    },
}
```

### Error Benefits

1. **Type safety**: Each aggregate has its own error type
2. **Rich context**: Include relevant data in errors
3. **Clear messages**: Descriptive error messages for debugging
4. **Domain language**: Errors use ubiquitous language

### Using Aggregate Errors

Business methods return `Result<T, A::Error>` and operate on `AggregateRoot<A>`:

```rust
// Commands are implemented on AggregateRoot<BankAccount>
impl AggregateRoot<BankAccount> {
    fn withdraw(&mut self, amount: i64) -> Result<(), BankAccountError> {
        if amount <= 0 {
            return Err(BankAccountError::InvalidAmount(amount));
        }

        if self.balance < amount {
            return Err(BankAccountError::InsufficientFunds {
                balance: self.balance,
                requested: amount,
            });
        }

        // Create and apply event
        let event = AccountWithdrawnEvent {
            amount,
            timestamp: Utc::now(),
        };

        // apply() validates, updates state, increments version, and tracks the event
        self.apply(event)
    }
}
```

## Business Logic

Business logic methods enforce invariants and create events.

### Command Pattern

Commands are methods implemented on `AggregateRoot<Entity>` that change state through events:

```rust
// Implement commands on AggregateRoot<BankAccount>
impl AggregateRoot<BankAccount> {
    /// Open a new account (factory method)
    fn open(owner: String, initial_balance: i64)
        -> Result<Self, BankAccountError>
    {
        let mut account = AggregateRoot::<BankAccount>::new(EntityId::new());

        let event = AccountOpenedEvent {
            owner,
            initial_balance,
            timestamp: Utc::now(),
        };

        // apply() validates, updates state, and adds to pending_events
        account.apply(event)?;

        Ok(account)
    }

    /// Deposit money (command)
    fn deposit(&mut self, amount: i64) -> Result<(), BankAccountError> {
        let event = AccountDepositedEvent {
            amount,
            timestamp: Utc::now(),
        };

        // apply() validates, updates state, and adds to pending_events
        self.apply(event)
    }

    /// Freeze account (command)
    fn freeze(&mut self) -> Result<(), BankAccountError> {
        let event = AccountFrozenEvent {
            timestamp: Utc::now(),
        };

        self.apply(event)
    }
}
```

**Note**: Commands operate on `AggregateRoot<BankAccount>`, which provides `Deref<Target = BankAccount>` for read-only access to entity fields (e.g., `self.balance`, `self.status`). All state mutations go through `self.apply(event)`.

### Query Pattern

Query methods return aggregate state without modification. Thanks to `Deref`, you can access entity fields directly through `AggregateRoot`:

```rust
impl AggregateRoot<BankAccount> {
    /// Get current balance (query)
    fn balance(&self) -> i64 {
        self.balance  // Deref allows direct access to entity fields
    }

    /// Get account status (query)
    fn status(&self) -> AccountStatus {
        self.status
    }

    /// Check if account can accept deposits (query)
    fn can_deposit(&self) -> bool {
        self.status == AccountStatus::Active
    }
}

// You can also implement queries on the entity itself
impl BankAccount {
    pub fn available_balance(&self) -> i64 {
        self.balance
    }

    pub fn can_deposit(&self) -> bool {
        self.status == AccountStatus::Active
    }
}
```

## State Management

Aggregates manage state through event application.

### Apply Event Method

Event dispatching is handled by the `EventApplicator` trait, which is **auto-generated** when you use the `aggregate` attribute on your Event enum:

```rust
// In your event enum definition:
#[derive(Event, Debug, Clone, Serialize, Deserialize)]
#[event(version = 1, type_prefix = "Account", aggregate = "BankAccount")]
//                                              ^^^^^^^^^^^^^^^^^^^^^^^^^^
//                                              This auto-generates EventApplicator!
enum AccountEvent {
    Opened(AccountOpenedEvent),
    Deposited(AccountDepositedEvent),
    Withdrawn(AccountWithdrawnEvent),
}

// You implement ApplyEvent for each event struct.
// Events apply directly to &mut BankAccount (the entity), not AggregateRoot.
impl ApplyEvent<BankAccount> for AccountDepositedEvent {
    fn validate(&self, account: &BankAccount) -> Result<(), AccountError> {
        // Validation logic...
        Ok(())
    }

    fn apply(&self, account: &mut BankAccount) {
        account.balance += self.amount;  // Direct entity mutation
    }
}

// The macro GENERATES an EventApplicator impl:
// impl EventApplicator<BankAccount> for AccountEvent {
//     fn dispatch(&self, entity: &mut BankAccount) -> Result<(), AccountError> {
//         match self {
//             AccountEvent::Deposited(e) => { e.validate(entity)?; e.apply(entity); e.post_validate(entity)?; }
//             // ... other variants
//         }
//         Ok(())
//     }
//     fn dispatch_unchecked(&self, entity: &mut BankAccount) { ... }
// }
```

**Key Point**: Events apply directly to `&mut BankAccount` (the entity). `AggregateRoot<BankAccount>` orchestrates the lifecycle (validate, apply, increment version, record event) but the actual state mutation targets the entity.

### Apply Rules

1. **Pure state transformation**: No side effects
2. **Deterministic**: Same event = same result
3. **No validation**: Trust that events are valid
4. **Idempotent**: Can be called multiple times safely

### Event Replay

Reconstruct aggregate state from events using `apply_unchecked`:

```rust
// Reconstruct from event history
let id = EntityId::new();
let mut account = AggregateRoot::<BankAccount>::new(id);

// Replay all events without validation
for event in historical_events {
    account.apply_unchecked(&event);
}
```

**Key difference**: `apply_unchecked` skips validation because historical events are assumed to be valid. This is important for performance during replay.

## Best Practices

### 1. Single Responsibility

Each aggregate should have a clear, focused purpose:

```rust
// Good: BankAccount handles account operations
// Good: Order handles order lifecycle
// Good: User handles user profile

// Bad: UserAccountOrder handles everything
```

### 2. Protect Invariants

Enforce business rules before creating events:

```rust
// Good:
fn withdraw(&mut self, amount: i64) -> Result<(), Error> {
    if self.balance < amount {
        return Err(Error::InsufficientFunds);
    }
    // Create event...
}

// Bad:
fn withdraw(&mut self, amount: i64) {
    // No validation, just create event
    let event = Withdrawn { amount, timestamp: Utc::now() };
    self.apply(event).unwrap();
}
```

### 3. Small Aggregates

Keep aggregates focused and small:

```rust
// Good:
struct Order {
    id: EntityId,
    items: Vec<OrderItem>,  // Small collection
    status: OrderStatus,
}

// Bad:
struct Order {
    id: EntityId,
    items: Vec<OrderItem>,  // Could be huge!
    customer: Customer,     // Should be a reference
    payment_history: Vec<Payment>,  // Separate aggregate
    shipments: Vec<Shipment>,  // Separate aggregate
}
```

### 4. Async Operations

Don't perform I/O in aggregates:

```rust
// Good:
fn place_order(&mut self, items: Vec<OrderItem>) -> Result<(), OrderError> {
    // Pure business logic only
    let event = OrderPlacedEvent { items, timestamp: Utc::now() };
    self.apply(event)
}

// Bad:
async fn place_order(&mut self, items: Vec<OrderItem>) -> Result<(), OrderError> {
    // Don't do this!
    let inventory = fetch_inventory().await?;
    let price = calculate_price(&items, &inventory).await?;
    // ...
}
```

### 5. Constructor Pattern

Use `AggregateRoot::new()` with factory methods:

```rust
// Good:
impl AggregateRoot<BankAccount> {
    fn open(owner: String, initial_balance: i64)
        -> Result<Self, BankAccountError>
    {
        let mut account = AggregateRoot::<BankAccount>::new(EntityId::new());
        // Apply creation event...
        Ok(account)
    }
}

// Bad:
let mut account = BankAccount {
    id: EntityId::new(),
    owner: String::new(),
    // Manually setting fields bypasses events
};
```

### 6. Version Management

Let `AggregateRoot` handle versioning:

```rust
// Good:
fn deposit(&mut self, amount: i64) -> Result<(), Error> {
    let event = DepositedEvent { amount, timestamp: Utc::now() };
    self.apply(event)  // Version incremented automatically by AggregateRoot
}

// Bad:
fn deposit(&mut self, amount: i64) -> Result<(), Error> {
    self.balance += amount;  // Don't bypass apply!
    // Don't manage version manually!
    Ok(())
}
```

### 7. Testing Aggregates

Test behavior, not implementation:

```rust
#[test]
fn test_withdraw_reduces_balance() {
    let mut account = AggregateRoot::<BankAccount>::open(
        "Alice".to_string(),
        1000,
    ).unwrap();

    account.withdraw(300).unwrap();

    assert_eq!(account.balance, 700);  // Read via Deref
    assert_eq!(account.pending_events().len(), 2); // Open + Withdraw
}

#[test]
fn test_withdraw_insufficient_funds() {
    let mut account = AggregateRoot::<BankAccount>::open(
        "Alice".to_string(),
        100,
    ).unwrap();

    let result = account.withdraw(200);

    assert!(matches!(
        result,
        Err(BankAccountError::InsufficientFunds { .. })
    ));
}
```

## Advanced Topics

### Aggregate References

Reference other aggregates by `EntityId`:

```rust
struct Order {
    #[id]
    id: EntityId,
    customer_id: EntityId,  // Reference, not embedded
    items: Vec<OrderItem>,
}
```

### Eventual Consistency

Coordinate between aggregates using events:

```rust
// In Order aggregate
fn place_order(&mut self) -> Result<(), OrderError> {
    let event = OrderPlacedEvent { timestamp: Utc::now() };
    self.apply(event)
}

// Separate event handler updates Inventory aggregate
async fn handle_order_placed(event: OrderPlacedEvent, inventory: &mut AggregateRoot<Inventory>) {
    inventory.reserve_items(event.items).await;
}
```

### Aggregate Lifecycle

```rust
impl AggregateRoot<Order> {
    // Creation
    fn create(customer_id: EntityId) -> Result<Self, OrderError> {
        let mut order = AggregateRoot::<Order>::new(EntityId::new());
        // Apply creation event...
        Ok(order)
    }

    // State transitions
    fn confirm(&mut self) -> Result<(), OrderError> { ... }
    fn ship(&mut self) -> Result<(), OrderError> { ... }
    fn complete(&mut self) -> Result<(), OrderError> { ... }

    // Termination
    fn cancel(&mut self) -> Result<(), OrderError> { ... }
}
```

## Summary

Aggregates in event-sauce provide:

- **Type-safe domain models** with derive macros
- **Entity/AggregateRoot separation** for clean architecture
- **Clear separation** between business logic and infrastructure
- **Rich error handling** with aggregate-specific errors
- **Clear boundaries** for consistency and transactions
- **Event-driven state** with replay support
- **Business rule enforcement** with validation via ApplyEvent trait

### Quick Reference: Aggregate Pattern

| Aspect | Description |
|--------|-------------|
| **Entity** | Your struct with `#[id]` field of type `EntityId` |
| **Aggregate** | `Entity + type Event + type Error` |
| **AggregateRoot** | `AggregateRoot<A>` wrapper for version, pending events, apply |
| **ID** | `EntityId` (UUID-backed newtype, universal for all entities) |
| **Commands** | Methods on `AggregateRoot<Entity>` or via `command_handler!` |
| **Read Access** | Via `Deref<Target = Entity>` on `AggregateRoot` |
| **Mutations** | Only through `apply()` on `AggregateRoot` |

### Key Patterns

1. **Define aggregate** with `#[aggregate(event = "...", error = "...")]` and `#[id]` on the ID field
2. **Use `#[event(aggregate = "...")]`** to auto-generate `EventApplicator` dispatching
3. **Implement `ApplyEvent` trait** for each event struct (operates on `&mut Entity` directly)
4. **Implement commands** on `AggregateRoot<Entity>` or use `command_handler!` macro
5. **Access entity fields** via `Deref` for read-only access through `AggregateRoot`
6. **Let `AggregateRoot` manage** version and pending events
