## Overview

In event sourcing, each aggregate is an independent consistency boundary. But some business rules span multiple aggregates — for example, "no two users can have the same email address". Aggregate claims solve this by letting aggregates declare ownership of unique values that are enforced transactionally.

**Key properties:**

- **Transactional** — claims are validated within the same database transaction as event appends
- **Namespaced** — each claim has a type (e.g., `"User.email"`) to prevent collisions between different kinds of claims
- **SHA-256 hashed** — claim values are stored as hashes, preventing plaintext leakage (important for encrypted aggregates)
- **Automatic lifecycle** — claims are updated on every commit and released on aggregate deletion

## Defining Claims

### Using the Macro

The `#[aggregate(..., claims)]` attribute tells the macro to delegate to your `aggregate_claims()` method:

```rust
use event_sauce::prelude::*;
use serde_json::json;

#[aggregate(event = "UserEvent", error = "UserError", claims)]
#[derive(Default)]
struct User {
    #[id]
    id: EntityId,
    email: String,
    username: String,
}

impl User {
    fn aggregate_claims(&self) -> Vec<AggregateClaim> {
        vec![
            AggregateClaim::new("User.email", json!(&self.email)),
            AggregateClaim::new("User.username", json!(&self.username)),
        ]
    }
}
```

The `claims` flag generates:

```rust
// Generated by the macro
impl Aggregate for User {
    // ...
    fn claims(&self) -> Vec<AggregateClaim> {
        self.aggregate_claims()
    }
}
```

### Manual Implementation

If you implement `Aggregate` manually, override the `claims()` method directly:

```rust
impl Aggregate for Profile {
    type Event = ProfileEvent;
    type Error = ProfileError;

    fn claims(&self) -> Vec<AggregateClaim> {
        vec![
            AggregateClaim::new("Profile.email", json!(&self.email)),
        ]
    }
}
```

## How Claims Work

Claims are extracted from the aggregate's current state and enforced every time events are committed:

1. **On commit** — `aggregate.claims()` is called to get the current claims
2. **Transactional upsert** — each claim is upserted into the `aggregate_claims` table within the same transaction as events
3. **Conflict detection** — if another aggregate already holds a `(claim_type, claim_hash)`, the transaction fails with `Error::ClaimConflict`
4. **Cleanup** — claims for types no longer returned by `claims()` are automatically removed (allowing claim value changes)

### Database Schema (PostgreSQL)

```sql
CREATE TABLE {schema}.aggregate_claims (
    aggregate_id UUID NOT NULL,
    claim_type VARCHAR(255) NOT NULL,
    claim_hash BYTEA NOT NULL,           -- SHA-256 of the JSON-serialized claim key
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    UNIQUE (aggregate_id, claim_type),   -- one claim per type per aggregate
    UNIQUE (claim_type, claim_hash)      -- uniqueness across all aggregates
);
```

Two UNIQUE constraints enforce:
- Each aggregate can hold at most **one claim per type** (e.g., one email claim)
- Each `(type, value)` pair can be held by at most **one aggregate** (cross-aggregate uniqueness)

### Claim Value Updates

When an aggregate changes a claimed value (e.g., email change), the claim is updated automatically. The `ON CONFLICT ... DO UPDATE` upsert replaces the old hash for the same `(aggregate_id, claim_type)`. If the new value is already claimed by another aggregate, a `ClaimConflict` error is returned.

## Handling Conflicts

When a claim conflict occurs, `commit()` returns `Error::ClaimConflict`:

```rust
use event_sauce::Error;

let result = store.commit(&mut user).await;
match result {
    Ok(()) => println!("User saved successfully"),
    Err(ref e) if e.is_claim_conflict() => {
        // Extract conflict details
        if let Error::ClaimConflict { claim_type, claim_key, held_by } = result.unwrap_err() {
            println!("Conflict on {claim_type}: value {claim_key} already taken");
            if let Some(holder) = held_by {
                println!("Held by aggregate {holder}");
            }
        }
    }
    Err(e) => return Err(e.into()),
}
```

The error includes:
- `claim_type` — which claim namespace conflicted (e.g., `"User.email"`)
- `claim_key` — the attempted value (the original JSON, not the hash)
- `held_by` — the UUID of the aggregate that currently holds the claim (if retrievable)

## Composite Claims

For uniqueness across multiple fields, use structured JSON values:

```rust
impl Membership {
    fn aggregate_claims(&self) -> Vec<AggregateClaim> {
        vec![
            // Unique (group, user) pair
            AggregateClaim::new(
                "Membership.unique",
                json!({"group_id": self.group_id.to_string(), "user_id": self.user_id.to_string()}),
            ),
        ]
    }
}
```

The entire JSON value is SHA-256 hashed, so different field combinations produce different hashes.

## Claims and Encryption

Because claim values are stored as SHA-256 hashes (not plaintext), claims are safe to use with encrypted aggregates. After crypto-shredding (deleting the encryption key), the event data becomes unreadable but the claim hashes remain — there's no way to reverse a SHA-256 hash back to the original value.

```rust
#[aggregate(event = "UserEvent", error = "UserError", encrypted, claims)]
struct User {
    #[id]
    id: EntityId,
    email: String,  // Encrypted at rest, but claim hash is safe
}
```

## Claims and Delete Events

When an aggregate is deleted via a delete event, all its claims are automatically released. The `clear_claims` flag is set internally during `commit_deleted()`, which issues a `DELETE FROM aggregate_claims WHERE aggregate_id = $1`.

This means:
- Other aggregates can immediately claim the released values
- No manual cleanup is needed

## Backend Support

| Backend | Claims Enforced | Notes |
|---------|----------------|-------|
| **PostgreSQL** | Yes | Full transactional enforcement with UNIQUE constraints |
| **In-Memory** | No | Claims parameters are accepted but not validated |

The in-memory backend is intended for testing. If you need claim enforcement in tests, use the PostgreSQL backend with testcontainers.

## Best Practices

1. **Use descriptive claim types** — `"User.email"` is better than `"email"` to avoid collisions across aggregate types
2. **Keep claims derived from state** — `claims()` should be a pure function of the aggregate's current fields
3. **Handle conflicts gracefully** — return user-friendly error messages when `is_claim_conflict()` is true
4. **Use JSON values** — `AggregateClaim` accepts `serde_json::Value`, so you can claim strings, numbers, or composite objects
5. **Combine with validation** — claims enforce uniqueness at the store level; use event validation for business rule checks at the aggregate level
