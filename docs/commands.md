# Commands

An aggregate command written directly against `AggregateRoot` cannot say
"this only makes sense before the aggregate exists" or "only once it has been
deleted". Every handler accepts whatever the repository hands it and
re-derives the lifecycle it expects by hand. The `commands` feature gives that
handler a type and gives the repository a loop to run it in.

The pieces are independent of how the aggregate is persisted: the same
command runs against an event-sourced or a state-stored repository, because
both implement `Repository`.

```toml
event-sauce = { version = "0.1", features = ["commands"] }
```

## Command and Root

`Root<A>` is an aggregate at one of its three lifecycle states:

| Variant         | Meaning                                   |
|-----------------|-------------------------------------------|
| `Root::Missing` | no init event has been applied yet        |
| `Root::Active`  | created and not deleted                   |
| `Root::Deleted` | a delete event was applied (terminal)     |

A `Command<A, Ctx = ()>` takes the aggregate wherever it stands and returns it
wherever the command leaves it. It narrows with `root.missing()?`,
`root.active()?` or `root.deleted()?`; a mismatch becomes a
`CommandError::Lifecycle { expected, found }` instead of a panic or a silent
no-op. A refusal from the aggregate itself is a `CommandError::Domain`.

```rust
type Outcome = Result<Root<Account>, CommandError<AccountError>>;

struct Open(&'static str);
impl Command<Account> for Open {
    fn handle(&self, root: Root<Account>, _ctx: &()) -> Outcome {
        Ok(root.missing()?.open(self.0.to_owned())?.into())
    }
}

struct Deposit(i64);
impl Command<Account> for Deposit {
    fn handle(&self, root: Root<Account>, _ctx: &()) -> Outcome {
        let mut account = root.active()?;
        account.deposit(self.0)?;
        Ok(account.into())
    }
}

struct Close;
impl Command<Account> for Close {
    fn handle(&self, root: Root<Account>, _ctx: &()) -> Outcome {
        Ok(root.active()?.close()?.into())
    }
}
```

`open`, `deposit` and `close` here are generated by `aggregate_command!`
(see [Getting Started](getting-started.md)); a handler can equally call
`apply`, `apply_init` or `apply_delete` itself. A command that needs something
from outside, such as a clock or a read-only lookup, takes it as `Ctx` rather
than closing over it.

## Repository::execute

```rust
let executed = repo
    .execute(id, &Deposit(40), &(), RetryPolicy::default())
    .await?;
assert_eq!(executed.attempts.get(), 1);
```

`execute` loads the aggregate (a `Missing` root when nothing is stored yet),
runs the command, and saves whichever root it returned: `save` for `Active`,
`save_deleted` for `Deleted`, nothing for `Missing`. It returns `Executed`,
carrying the final `Root` and the number of attempts.

`execute` runs the command in an [event context](event-context.md): the events
it produces carry the command's `name()` as their `command`, and a correlation
id is added (a fresh UUID string) unless an enclosing scope already provides
one. `name()` returns `None` by default, so a command is anonymous until it
overrides it:

```rust
impl Command<Account> for Deposit {
    fn handle(&self, root: Root<Account>, _ctx: &()) -> Outcome {
        let mut account = root.active()?;
        account.deposit(self.0)?;
        Ok(account.into())
    }

    fn name(&self) -> Option<&str> {
        Some("Deposit")
    }
}
```

Failures come back as `ExecuteError`:

- `Load`: loading failed for a reason other than "nothing saved yet"
- `Domain` and `Lifecycle`: the command refused; nothing was written and the
  command is not retried
- `Save`: saving failed, including a concurrency conflict that outlived the
  retry budget

A command that returns a root under another id than the one requested is
rejected as `Save` rather than stored under the wrong identity.

## Retries

When the save loses a race to a concurrent writer, `execute` reloads the
aggregate and runs the command again from scratch, so the second attempt
decides on fresh state. Only a concurrency conflict is retried.

`RetryPolicy` carries the attempt budget and the backoff between attempts:

```rust
let policy = RetryPolicy::default() // 3 attempts, 10ms doubling up to 1s
    .with_max_attempts(NonZeroU32::new(5).unwrap())
    .with_initial_backoff(Duration::from_millis(50));

RetryPolicy::none() // one attempt, never retry
```

Because a command may run more than once it must be a pure function of the
root and the context: no side effects outside the aggregate.

## modify

`Repository::modify` is the closure form of a single attempt: it loads, runs
the closure once against the active aggregate and saves. A concurrency
conflict comes back as `ModifyError::Save` and is not retried, because a
`FnOnce` closure cannot be run twice. Reach for `modify` for a one-off change
at a call site (it adds the correlation id like `execute`, but has no command
name), and for `Command` with `execute` and a `RetryPolicy` when the
operation has a name, a lifecycle precondition, needs automatic retries, or
deserves to be tested on its own.
