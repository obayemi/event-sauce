# Changelog

All notable changes to event-sauce are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
This project has not yet reached 1.0, so breaking changes are called out
explicitly rather than gated behind a major version bump.

## [Unreleased]

### Breaking Changes

- **Policy causation merges into events that carry metadata.** An event
  recorded with `apply_with_metadata` used to keep its metadata untouched
  when a policy committed it, so it lost the cascade tracking. It now
  keeps every field it set and gains the ones it lacks: correlation id,
  tenant, command, correlation path, additional keys, and the causation id
  and chain together, the latter only when it set neither.
- **Correlation ids are strings.** `EventMetadata::correlation_id` is now
  `Option<String>`, `with_correlation_id` and `EventEnvelope::with_causation`
  take `impl Into<String>`, and `child_metadata` falls back to the parent
  event id rendered as a string. Stored JSON with a UUID-shaped or null
  `correlation_id` still deserializes. On Postgres, `migrate()` converts
  the `events.correlation_id` column from `UUID` to `TEXT`, which rewrites
  the events table under an `ACCESS EXCLUSIVE` lock: run it in a
  maintenance window on a large table.
- **`PolicyRunner::process_pending` returns `PolicyRunOutcome`, not
  `usize`.** `process_pending` now takes a per-policy lease (see Fixed,
  below), and a standby worker that currently holds none of them needs to
  be told apart from one that simply had nothing pending — both used to
  look like `Ok(0)`. `PolicyRunOutcome::Completed(usize)` carries the old
  count; `PolicyRunOutcome::Busy` is returned exactly when policies are
  registered but none of their leases could be acquired. Replace
  `let n = runner.process_pending().await?;` with
  `let n = runner.process_pending().await?.processed();` to keep the old
  count-only behavior, or match on the outcome to tell a busy standby apart
  from an idle one.
- **`AggregateRoot::restore` replaces `from_snapshot`, takes a
  `StoredVersion`, and can fail.** It's generic over whatever shape a store
  hands back: `AggregateRoot::restore(version, stored)` converts `stored`
  into the entity through `TryFrom`, returning a conversion failure as is.
  Passing the entity itself, or any type the entity implements `From` for,
  can never fail — its error type is `Infallible`, so the result
  destructures irrefutably on stable:
  `let Ok(root) = AggregateRoot::<A>::restore(version, entity);` — which is
  what every `Repository` does today, whatever the backing store —
  event-sourced snapshot-plus-tail or a state-stored row. The turbofish can
  go only where something downstream already pins `A`. `version` is a
  `StoredVersion`, a version of at least 1, the least a saved aggregate can
  have: convert the version read from storage with
  `StoredVersion::try_from(version)?`, which refuses a lower one with
  `InvalidStoredVersion` (it converts into
  `Error::InvalidState`, so `?` works in a function returning
  `event_sauce::Result`), or pass `StoredVersion::FIRST`. Callers building a
  root from a rehydrated entity replace `AggregateRoot::from_snapshot(..)`
  with `let Ok(root) = AggregateRoot::<A>::restore(version, entity);`.
- **A stored version below 1 is refused on load.** A state-stored row saved
  at such a version now fails `load`/`load_any`/`load_deleted` with an
  `Error::InvalidState` naming the aggregate type and id: the row is the
  source of truth, so it has to be repaired in place. An event-store
  snapshot at such a version is a cache miss instead: it is discarded and
  the aggregate is rebuilt by replaying its events.
- **Commands take their instant as a parameter, by default.** A command
  generated by `command_handler!` now takes every field of its event,
  instants included, unless the command is annotated `@clock`, in which case
  a `timestamp` field is stamped from `Utc::now()` as before. Add `@clock` to
  keep the old wall-clock-stamped behavior, or pass the instant explicitly.
- **`Repository` is dyn-compatible, and implementors take an `EntityId`.**
  `Box<dyn Repository<A>>` / `Arc<dyn Repository<A>>` now work, because the
  typed-id conveniences (`load`, `load_any`, `load_deleted`, `modify`,
  `create_with`, `create_with_id_and`, `exists`, `get_version`, …) moved
  behind a `where Self: Sized` bound and delegate to new `EntityId`-only
  methods that aren't. **Implementors break:** provide `load_by_id`,
  `load_any_by_id`, and `load_deleted_by_id` instead of the old generic
  `load`/`load_any`/`load_deleted` (`exists_by_id` and `version_by_id` have
  defaults built on `load_any_by_id`, so they're optional to override). A
  caller holding a concrete repository type is unaffected; a caller holding
  `dyn Repository<A>` calls the `*_by_id` methods directly, since the
  `Sized`-bound typed-id methods aren't available on it.
- **An event refused before `apply` no longer poisons the aggregate root —
  through `apply`/`apply_with_actor`.**
  `AggregateRoot::apply`/`apply_with_actor` now distinguish a pre-validation
  refusal (nothing mutated, caught by `EventApplicator::validate_only`) from
  a failure that already ran the apply closure: only the latter poisons the
  root. `define_events!` and `#[derive(Event)]` both generate
  `validate_only` — from `@validate` and from each variant's
  `ApplyEvent::validate` respectively — so the split is the same whichever
  of the two defines the event. Only a fully hand-written `EventApplicator`
  impl that leaves `validate_only` at its default `Ok(())` still poisons on
  *every* failure, mutated or not. `apply_with_metadata` also still poisons
  on every failure — it calls `dispatch` directly and never calls
  `validate_only`. A caller that did `let _ = aggregate.command(..)` to
  absorb an expected refusal through `apply`/`apply_with_actor` can now keep
  using the aggregate afterward, where it previously had to discard and
  reload it. Poisoning still means `Error::InvalidState` on the next
  commit/save — see
  [aggregate_root.rs](crates/event-sauce-core/src/aggregate_root.rs) for the
  precise rule (only the commit/save path checks it; further `apply*`/
  `apply_delete*` calls do not). A derived or `define_events!` event now
  runs `ApplyEvent::validate` twice per `apply`/`apply_with_actor` call —
  once through `validate_only`, again inside `dispatch` — so `validate`
  must be pure and deterministic.
- **`dispatch_policies_to_outbox`'s checkpoint and lease move from one name
  per policy set to one name per policy**
  (`__policy_outbox_dispatcher:{policy}`). Each policy's lease is now
  acquired and dispatched independently; the call returns `Busy` only when
  *none* of them could be held, where it previously returned `Busy`/
  `Completed` for the whole set together. **Upgrade effect:** on first run
  after upgrading, each policy's new `__policy_outbox_dispatcher:{policy}`
  checkpoint is seeded once from the old shared `__policy_outbox_dispatcher`
  row, so an existing dispatcher resumes every policy right where the
  shared dispatcher had stopped — no backfill, no re-enqueue. The legacy row
  is never written again after that, only read: a policy added *later*, on
  a deployment that has ever run the shared dispatcher, is also seeded from
  that same frozen position; a deployment that never had a legacy row
  starts it from genesis instead. Either way, **this is that policy's
  first delivery of every event since its starting point, not a replay** —
  its handler runs for that whole history, which can be substantial on a
  long-lived log. To start a newly registered policy at the current head
  instead, pre-seed its `__policy_outbox_dispatcher:{policy}` checkpoint
  before the first call that names it; seeding never overwrites an
  existing row. A *re*scan of a policy already past its starting point is
  a different matter and is idempotent *only while the resulting `done`
  rows are still in the outbox*: `UNIQUE(policy_name, event_id)` with `ON
  CONFLICT DO NOTHING` makes re-enqueuing an already-processed event a
  no-op. Once [`prune_done`](#added) has removed those rows, a rescan
  re-delivers the event and re-runs its handler.
- **`mark_failed` on both outboxes now takes a `BackoffPolicy`** and sets the
  row's `locked_until` into the future (exponential, capped, jittered)
  instead of clearing it, so a transient failure no longer lets every
  polling worker hot-loop-retry the same rows on the next sweep.
  `StateOutboxDispatcher` gained `with_backoff` (default: 1s base, 5 minute
  cap, 50% jitter). Callers passing their own retry loop around `mark_failed`
  should account for the new backoff delay before a row becomes claimable
  again.
- **`mark_done` and `mark_failed` on both outboxes now take the claiming
  `worker_id` and return `Result<AckOutcome>`** instead of `Result<()>`.
  `AckOutcome::Fenced` means the ack was fenced out — the caller's claim on
  that row already expired and was reclaimed by another worker, so the row
  was left untouched. Callers must pass their worker id and handle the
  outcome, typically by treating `Fenced` as "someone else owns this row
  now" rather than as an error.
- **`EveryNEvents` wraps a `NonZeroU32`**, not a public `u32` tuple field, so
  `EveryNEvents(0)` can no longer be constructed at all — it previously
  compiled and only panicked later, inside the commit path, on first use.
  Construct it with `EveryNEvents::new(NonZeroU32)` or the fallible
  `EveryNEvents::try_new(u32)`.
- **`CryptoKeyStore` gains `get_or_insert_key`**, an atomic
  insert-if-absent operation with no default body: every implementor
  (custom key stores included) must now provide one (e.g. a `HashMap::entry`
  under one write lock, or `INSERT ... ON CONFLICT ... RETURNING`), so
  concurrent first commits of the same aggregate converge on one key
  instead of racing. Custom stores must also meet the wider shredding
  contract this release adds: `get_or_insert_key` MUST refuse a shredded
  aggregate atomically, returning `Error::key_not_found` and inserting
  nothing, in the same step as the insert-if-absent check; `delete_key`
  must leave that shredded state observable instead of just removing the
  row; and `upsert_key` clears the marker (an explicit key rotation always
  un-shreds). "Has a key" and "is shredded" are mutually exclusive states
  a store must never let a reader observe both of at once. Added:
  `CryptoKeyStore::is_shredded` — a fast-path hint for a caller that wants
  to reject a shredded aggregate before doing any encryption work; it
  defaults to `false`, so a store that tracks shredding only through
  `get_or_insert_key`'s refusal should override it to answer truthfully.
- **Test fixtures are no longer part of the public API** of
  `event-sauce-core`. A crate depending on them directly (rather than
  through the normal store/repository API) needs to vendor or reimplement
  whatever it used.
- **The `crypto` feature is opt-in everywhere, not just on the facade.**
  `event-sauce-memory` and `event-sauce-postgres` no longer default to
  installing `Aes256GcmProvider`: `crypto` moved out of both crates' default
  features. A crate depending on `event-sauce-memory` or
  `event-sauce-postgres` directly, with default features, that commits or
  loads an encrypted aggregate now gets
  `InvalidState("Encrypted aggregate requires crypto_provider")` where it
  previously got a provider for free. Enable the `crypto` feature on
  whichever entry point you depend on, or pass `.crypto_provider(...)`
  explicitly on the builder, to keep the old behavior.
- **The memory backend now honors the `event-sourcing`/`state-store`
  feature flags it's paired with**, instead of always compiling both.
  `event-sauce = { default-features = false, features = ["memory"] }` now
  exports nothing from `event_sauce::memory`; add `event-sourcing` and/or
  `state-store` to get `InMemoryEventStore`/`InMemoryStateStore` back. With
  default features (which include both), nothing changes. (`event-sauce-postgres`
  still requires both core features regardless of which facade flag is
  enabled — its state store calls into the event store for claim
  enforcement, so the two aren't separable yet.)

### Added

- Ambient event context. `EventContext` (a `Root` context starts a new flow
  and may carry a tenant, a nested one cannot), the `event_context!` macro,
  the `#[with_event_context]` attribute, `WithEventContextExt::with_event_context`
  for futures, `EventContext::current` to hand the context to a spawned task,
  and `entered`/`in_scope` for synchronous code. Events applied inside a scope
  get `tenant`, `correlation_id`, `correlation_path`, `command` and
  `additional` on their `EventMetadata`. Values convert through
  `Into<serde_json::Value>`, and the `%` sigil stores any `Display` type.
  `Uuid` goes through `%id`, `DateTime` needs `%at` or
  `at.to_rfc3339()`, `i128`, `u128` and `char` need `%`, and references
  such as `&String` need `.as_str()` or a clone. See
  `docs/event-context.md`.
- `Command::name` and `UnitOfWorkCommand::name` record a command's name on
  the events it produces. `Repository::execute`, `Repository::modify` and
  `UnitOfWorkStore::execute` also add a correlation id when no scope
  provides one, and policy reactions run in a root context seeded from the
  source event.
- Postgres persists `causation_chain`, `tenant`, `command` and
  `correlation_path`.
- `EventStore::fetch_batch` — fetches up to `limit` events after a
  position and drops the underlying stream before returning, for
  consumers (like `PolicyRunner`) that need a bounded, already-materialized
  batch rather than an open-ended stream.
- `PolicyRunner::with_worker_id`/`with_lease_duration`/`with_batch_size` —
  configure the identity, lease duration, and fetch batch size
  `process_pending` uses (sensible defaults: a generated per-instance id,
  30s, 500 events).
- `CheckpointStore::seed_checkpoint` — seeds a subscription at a position if
  it has none yet, without overwriting one that does. The provided default
  is load-then-save and racy under concurrent seeders, so a custom backend
  should override it; `InMemoryCheckpointStore` and `PostgresCheckpointStore`
  already do, with a single atomic insert-if-absent (`entry().or_insert`,
  `INSERT ... ON CONFLICT DO NOTHING`). `PolicyRunner` uses this to seed a
  never-before-seen policy, so a slower worker's seed never overwrites
  progress another worker already made under its lease.
- `CheckpointStore::save_checkpoint_fenced` — saves a checkpoint only while
  `worker_id` still holds the lease, returning `Error::LeaseLost`
  otherwise. The provided default is `renew_lease` then `save_checkpoint`,
  which leaves a race window; `InMemoryCheckpointStore` and
  `PostgresCheckpointStore` override it with one atomic check-and-write,
  and a custom backend should do the same.
- `StoredVersion` — an `AggregateVersion` of at least 1, the version type
  `AggregateRoot::restore` takes — and `InvalidStoredVersion`, the error its
  `try_from` returns for a lower version.
- `PostgresBackend::run_sticky_projection` — a leased projection runner that
  holds its lease across idle ticks (renewing and re-draining in a loop)
  instead of releasing and reacquiring it on every call, removing the
  contended relock every `NOTIFY` used to cause on every node.
- `PostgresPolicyOutbox::prune_done` — deletes old `'done'` outbox rows in
  bounded batches, since nothing removed them automatically before
  (`mark_done` only flips status, by design, to keep idempotency). The
  state outbox has no equivalent yet: its `mark_done` deletes the row
  outright, so it has no `'done'` rows to accumulate.
- `aggregate_command!` — the new name of `command_handler!`, saying that it
  generates aggregate commands rather than a service command handler.
- `commands` feature — `Command<A, Ctx = ()>`, a typed, lifecycle-aware
  command handler; `Root<A>`, an aggregate at whichever of its three
  lifecycle states (`Missing`/`Active`/`Deleted`) a command needs to match
  on or narrow with `?`; `Lifecycle` and `CommandError<E>`, turning a
  lifecycle mismatch into a typed error instead of a panic or a silent
  no-op; `RetryPolicy`, the attempt count and backoff a retry loop runs
  on; `ExecuteError` (`Load`/`Domain`/`Lifecycle`/`Save`) and `Executed`
  (the final `Root` plus the attempt count), the error and result of
  `execute`.
- `Repository::execute` — runs a `Command` against an aggregate's current
  lifecycle state and saves wherever it leaves it, retrying the whole
  load/handle/save cycle on a concurrency conflict up to a `RetryPolicy`'s
  attempt budget.
- `unit-of-work` feature — `UnitOfWorkStore`, `UnitOfWork`,
  `UnitOfWorkCommand` and `Tracked`: a command that loads, creates and
  changes any mix of event-sourced and state-stored aggregates, committed
  in one atomic `TransactionalStore::commit_atomic` call that also asserts
  every aggregate the command only read is still at the version it loaded,
  retrying the whole command on a concurrency conflict. The backend-facing
  contract is `TransactionalStore`, `AtomicCommit`, `PreparedWrite`,
  `StreamWrite`, `Expectation` and `UnitOfWorkRepository`; commands return
  `UnitOfWorkExecuted` or fail with `UnitOfWorkError`.
  `InMemoryTransactionalStore` and `PostgresTransactionalStore` implement
  `TransactionalStore` for the two built-in backends. The Postgres one
  requires both stores to share one database:
  `PostgresTransactionalStore::new` returns `Error::InvalidState` when the
  two pools differ in host, port or database.

### Deprecated

- `command_handler!` — renamed to `aggregate_command!`. It still expands to
  the same code and warns at each call site; replace
  `command_handler! { impl Order { ... } }` with
  `aggregate_command! { impl Order { ... } }`.

### Fixed

- `PostgresEventStore` now persists `EventMetadata::causation_chain`. It
  used to store the causation id only, so a stored event read back with an
  empty chain and `PolicyRunner::max_cascade_depth` never stopped a
  cascade on Postgres. `migrate()` adds the column; events stored before
  the fix keep an empty chain, so their cascades restart counting from
  zero.
- `InMemoryEventStore::append_batch` is now atomic: every commit's expected
  version is checked under one pair of write locks before any commit in the
  batch is applied, so a batch that fails partway leaves every stream
  untouched instead of persisting the commits that came before the failure.
- `PolicyRunner::process_pending` now drains events in bounded
  `EventStore::fetch_batch` calls (configurable via
  `PolicyRunner::with_batch_size`, default 500) instead of holding one
  open-ended `stream_all` stream for the whole call — a connection or
  MVCC snapshot the store holds for a fetch no longer outlives the
  handlers that run between fetches, so a slow handler no longer pins a
  pooled connection or the vacuum horizon for the length of a whole catch-up
  run. `PostgresEventStore` overrides the new `EventStore::fetch_batch`
  (default: `stream_all` bounded by `limit`) with its existing
  `fetch_events_batch`. Checkpoints are saved after every batch instead of
  only once at the end, so a cancellation or a transient error partway
  through replays at most the batch in flight, never the whole call.
  Delivery stays at-least-once.
- `PolicyRunner::process_pending` is now safe to call from more than one
  process or pod: each registered policy is its own lease, acquired and
  renewed through the configured `CheckpointStore`
  (`try_acquire_lease`/`renew_lease`, mirroring the `PostgreSQL` projection
  runners), with checkpoint saves fenced on it via the new
  `CheckpointStore::save_checkpoint_fenced` (`InMemoryCheckpointStore` and
  `PostgresCheckpointStore` override the provided default with a single
  atomic check-and-write). A never-before-seen policy is seeded through the
  new, atomic `CheckpointStore::seed_checkpoint` instead of a racy
  load-then-save, and a seed or acquire failure releases every lease
  already acquired earlier in that same call instead of leaving them held
  until they expire. A per-policy lease alone doesn't stop two concurrent
  calls *on the same runner instance* (same worker id) from both acquiring
  it, so `process_pending` also serializes internally — a second
  concurrent call on the same instance waits for the first rather than
  racing it. Held leases are renewed through every backoff sleep and
  before every attempt of an `OnError::Retry`, so a long
  `RetryLimit::Indefinite` or `RetryLimit::MaxDuration`/`max_delay` keeps
  its lease instead of silently outliving it; if the lease is lost anyway,
  the retry aborts with `Error::LeaseLost` rather than running alongside
  the new holder. Renewal is also checked on every fetched event (matched
  or not) and again before every matching policy's handler call, so a held
  policy sitting ahead of the scan position (e.g. a checkpoint reset for a
  replay) is covered too. A single handler call still longer than roughly
  two thirds of `lease_duration` can lose the lease before a renewal lands
  — see `docs/policies.md`'s Multi-Instance Safety section.
- Postgres claim conflicts now wait instead of risking a deadlock, and a
  racing claim correctly reports `ClaimConflict` rather than a generic
  error.
- Concurrent `migrate()` calls across nodes no longer conflict.
- A snapshot race during concurrent commits keeps the newest snapshot
  instead of a stale one.
- Projections now checkpoint past unmatched events in a fetched batch, so a
  low-match-rate projection doesn't re-scan the same already-known-irrelevant
  events on every run.
- Slow outbox batches no longer ack rows whose lease has since expired and
  been reclaimed by another worker.
- `PolicyContext::flush()`'s `ConcurrencyConflict` now obeys the configured
  `OnError` (`Retry`/`Skip`/`Fail`) instead of always aborting
  `process_pending` regardless of it.
- Lease loss from `InMemoryCheckpointStore::renew_lease` now reports as
  `Error::LeaseLost` (so `is_lease_lost()` works) instead of a stringly
  `Error::Custom`.
- A failed or cancelled save (a `ConcurrencyConflict`, or one failed stream
  in a `save_all` batch) no longer silently drops the aggregate's pending
  events while leaving its version advanced — a retried save now actually
  retries instead of writing nothing and returning `Ok`.
- Deleting a crypto key now leaves a shredded tombstone (memory: an id set;
  Postgres: a nullable `key_data` plus a new `shredded_at` column, added as
  its own migration step and enforced by a `crypto_keys_shred_state` CHECK
  constraint requiring exactly one of the two to be set) instead of removing
  the row outright, so a stale or concurrent writer can no longer regenerate
  a key and write fresh PII for an aggregate that was crypto-shredded.
- A crate using `define_events!`/`command_handler!` needs no direct
  dependency beyond `event-sauce`/`event-sauce-core` and `serde` (with the
  `derive` feature) — the macros no longer require the caller to add
  `paste`, `uuid`, `serde_json`, `chrono`, or `async-trait` themselves.

### Changed

- `Repository::modify` is now built on `Repository::execute` internally;
  its signature and behaviour are unchanged.
- Postgres appends hold the global append-serialization lock for less of
  their critical section.
- The policy dispatcher batches its checkpoint writes per fetched batch (up
  to 500 events) instead of one write per event, so dispatch lag against a
  large log with a low match rate no longer scales with total event volume.
- The macros' internal `paste` dependency (unmaintained, RUSTSEC-2024-0436)
  is replaced by its maintained fork, `pastey`. Callers of
  `define_events!`/`command_handler!` are unaffected either way, since
  neither was ever a direct dependency.

### Migration Steps

- `add_crypto_keys_shredded_at` — relaxes `crypto_keys.key_data` to nullable,
  adds the `shredded_at` marker column, and adds the
  `crypto_keys_shred_state` CHECK constraint
  (`(key_data IS NULL) = (shredded_at IS NOT NULL)`). Runs automatically the
  next time `store.migrate()` is called; **fails on any existing row where
  both `key_data` and `shredded_at` are set, or neither is** — clean up such
  rows before upgrading.
